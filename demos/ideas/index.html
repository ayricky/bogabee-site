Payments

Stripe, called from Cloudflare Pages Functions. The site already runs on Cloudflare Pages, and the event check-in work in PR #4 added Functions, a D1 database and HubSpot, so orders slot into the same setup.

  1. The cart lives in the browser. Checkout sends only product IDs and quantities to /api/checkout.
  2. The server reads prices and stock from D1, recomputes the total, and creates a Stripe Checkout Session. The browser's prices are never trusted.
  3. The customer pays with a card, Apple Pay or Google Pay on Stripe's hosted page, or in an embedded Payment Element styled like the demo.
  4. Stripe's checkout.session.completed webhook records the order in D1, reduces stock, and for porch pickup creates the cabinet code.
  5. The customer gets a receipt and the order page. Danny sees the order in the hub and gets a text or email.

Cost

No monthly fee. Stripe's standard US online card rate is 2.9% + 30¢ per payment, so a $16 jar costs about 76¢ to process.

At markets and events

Stripe's Tap to Pay on iPhone takes cards and phones at the table with no reader, and those sales can come off the same stock count as the website once the two are connected.

Self-serve pickup

Unlocking the porch cabinet

Customers already come to the house and take honey from a cabinet on the front porch. Paying online lets each order carry its own code for that cabinet. Four ways to do it:

Keypad padlock with offline codes: igloohome Smart Padlock 2

Recommended

A keypad padlock on a hasp across the cabinet doors. It has steel-capped buttons, an IPX7 waterproof rating and a rechargeable battery, and needs no Wi-Fi or outlet. About $159 from igloohome. The commercial Padlock 2E is rated IP68 if the cabinet gets direct weather.

Good
  • One code per order, used once, expiring on its own
  • Checks codes offline, so a Wi-Fi outage can't lock anyone out
  • The lock records every open
Watch
  • A code can't be cancelled remotely before it expires
  • A limited number of one-time codes can start in the same time slot (5 through Seam), so busy pickup times need spreading
  • The battery needs recharging a few times a year (igloohome quotes up to about nine months per charge)

Wi-Fi smart lock

A lock on the home Wi-Fi with an "Open cabinet" button on the order page.

Good
  • Unlimited codes, instant revoke
  • Opens from the phone, no typing
Watch
  • Needs Wi-Fi reaching the porch
  • Stops working when the Wi-Fi does

One shared code, changed weekly

A basic keypad lock. The order page shows this week's code.

Good
  • Cheapest, no integration
Watch
  • Anyone who paid once knows the code all week
  • No record of who opened it

Unlocked, pay by QR

Keep the cabinet as an honor box, with a QR sticker for paying on the spot.

Good
  • No hardware at all
Watch
  • Relies on trust, like today

How the padlock connects to the site

  1. Danny sets up the padlock in the igloohome app, then turns on API access in igloohome's developer portal (iglooaccess). The client ID and secret go into Cloudflare as secrets.
  2. When Stripe confirms a porch pickup, the server asks igloohome for a one-time code starting at the chosen pickup time. It works for 24 hours and stops after one use.
  3. The code is saved with the order and shown on the receipt, in the email, and by text if we add it.
  4. The padlock checks the code itself. The igloohome servers and the padlock compute the same codes, so nothing has to be sent to the porch.
  5. The padlock records each open. Those records reach the hub when the igloohome app syncs near the cabinet, or close to real time with igloohome's Bridge. The Bridge plugs in within a meter of the padlock. Until then, the customer's "I picked up my honey" button marks the order.

Cost: igloohome lists API access from $2 per active lock per month. Seam is an alternative layer over the same API; it's free for up to 3 devices and gives cleaner webhooks, but may still need igloohome's API plan behind it. Either works with the same site code.

Either way, a QR sticker on the cabinet

The cabinet page covers both kinds of visitor: someone who ordered ahead looks up their code, and someone who just drove by buys what's in the cabinet and gets a code on the spot. Stock in the cabinet is tracked separately from the website, so the hub knows when to restock.

Event sign-in

A QR code on the table opens a short sign-in form. A tablet can run it as a kiosk that clears after each guest. Each sign-in becomes a HubSpot contact tagged with the event; returning customers keep their history. The hub shows sign-ins live, prints the table sign and exports the list.

The backend for this is already built in PR #4 (paused): the HubSpot form and property exist, and D1 holds the events. The demo is the front end it would get.

Edited from the hub

Apiary page and Journal

Danny edits the Apiary page and writes Journal posts in the hub, with no developer in the loop. Posts have drafts, a private preview, a cover photo and simple formatting: headings, bold, lists, links, quotes and photos.

  1. The hub sits behind Cloudflare Access, the same sign-in planned for the event dashboard in PR #4, so only Danny's account can edit.
  2. Posts and page text are saved in D1. Photos are shrunk in the browser and uploaded to Cloudflare R2.
  3. The server cleans every post to a short list of allowed tags before saving, so a pasted script or styling can't reach the public site.
  4. Public pages are rendered on the server and cached, so they load fast and search engines can read them. Drafts show only through Danny's preview link.
  5. Each save keeps the previous version, so an edit can be rolled back.

For search engines, the Journal also gets an RSS feed and a sitemap, and draft previews and the hub are marked not to be indexed.

The demo stores everything in the browser instead, so edits show up on the public pages in other tabs right away but aren't shared between devices.

CRM

HubSpot

Every place a customer meets the site updates Bogabee's HubSpot account (portal 247317631). The HubSpot screen in the hub shows what synced, what's queued and what failed, with Retry.

  1. Event sign-ins create or update a contact. New people become leads; people HubSpot already knows keep their stage. Each sign-in sets Last Bogabee event (bogabee_last_event) and their interests. This is the PR #4 flow, unchanged.
  2. Paid orders, online or from the porch cabinet, update the contact to Customer and add a closed-won deal in an Online orders pipeline, with the amount, the jars and how it's fulfilled. A walk-up with no email gets the deal without a contact.
  3. Party favor quotes add a deal in a Party favors pipeline that moves as the quote does: New request, Label approval, Payment link sent, Paid.
  4. Harvest news subscribes a contact to a Harvest news email list only when they ask: the box at an event or at checkout, or the Journal sign-up.
  5. Contacts are matched by email, then by phone. A phone number that matches more than one contact is never merged.

To go live

  • The HUBSPOT_TOKEN secret from PR #4 is already in Cloudflare. Its private app needs two more scopes: deals (crm.objects.deals.write) and email subscriptions (communication_preferences.write).
  • Create the Online orders and Party favors pipelines, the Harvest news subscription type, and the properties for interests and fulfillment.
  • Syncs run on the server after Stripe confirms a payment or a form is sent, and retry on their own when HubSpot is slow.
